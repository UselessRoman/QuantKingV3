# QuantKing 架构设计

先读仓库根 [AGENTS.md](../../../AGENTS.md)，再读 [决策](../../../docs/DECISIONS.md)、
[实施计划](../../../docs/IMPLEMENTATION_PLAN.md)、[技术标准](../../../docs/TECHNICAL_STANDARDS.md)
及当前任务涉及的阶段卡。状态从 [路线图](../../../docs/ROADMAP.md) 核实；只按本次问题补读
数据、研究回测、交易风险或 Web 领域文档，不全库展开历史记录。

## 确定要解决的决策

区分用户是在探索方案、要求只读评审、授权更新设计文档，还是已经授权实现。保持用户指定的
顺序；已授权的设计工作直接完成，不能因本技能再次索要相同确认。仅讨论时在回复中给出方案，
不落地架构文档或业务实现。规划后续阶段不构成实施授权。

核实当前实现的入口、领域服务、持久化与真实消费方。已有能力、未来目标、未经验证的假设分别
标明，特别留意当前工作树的未提交改动。输出要回答具体决策，不预设必须重构。

## 从完整链路推导最小设计

围绕本次目标梳理“触发 → 显式输入版本 → 应用服务 → 领域规则 → 适配器/存储 → 发布或失败
→ API/Web 反馈 → 验收”。标出本 Stage 负责的部分和后续消费契约，不实现未来节点。涉及状态
和长任务时说明谁拥有状态、中断后如何判定、何时允许安全重试、用户在哪里看到失败。

契约按需写清主键、单位、缺失语义、业务日期、可用时间、版本血缘、输出及失败类型。研究问题
尤其检查 point-in-time：历史股票池、复权、标签窗口与切分是否可能读取未来信息。日线共识
遵循 ADR-004/021，研究参考字段遵循 ADR-029，不能混用两套来源要求。

给出最小可行方案及确有取舍的替代方案；无需为简单决定凑方案数量。比较正确性、当前交付成本、
Windows 离线运行、兼容/迁移、可恢复性和验收成本。建议新增状态机、仓储、`Protocol` 或证据
类型前，指出当前调用者，以及现有 Job、manifest、原子发布和日志不能表达的实际需求。
优先复用已有机制；不得为五种逻辑版本建立五套控制面或为未来阶段预建平台。

## 用反例检验方案

选择与本次变化有关的反例：上游缺行/冲突、晚到修订、未来数据扰动、部分写入、进程中断、
同输入重复提交、版本已发布、输入范围越界。逐项说明应拒绝、隔离、复用还是新建版本，以及
如何观察和复验；不机械要求所有设计跑全套场景。

存在可独立审查的重大设计时，委派只读代理从原始需求和当前实现挑战契约、简化空间与漏项。
主代理核实反馈，给出取舍依据和剩余不确定性；代理一致意见不能代替测试或用户决策。

## 形成可实施结果

已授权写文档时，先更新决策和受影响文档，再进入已授权实现。ADR 记录决定和后果，任务卡记录
Stage、依赖、允许/禁止范围、契约、输出、测试、验收与外部授权边界；执行事实写实施/验收记录，
阶段状态只更新路线图。不复制多份合同，不改写冻结失败证据。

交付说明推荐方案、关键取舍、可验证的接受条件，以及确实需要用户选择的未决项。实现授权尚未
覆盖的部分保持为建议。若已授权设计和实现且没有阻断决定，转入编码流程完成，不停在建议阶段。
