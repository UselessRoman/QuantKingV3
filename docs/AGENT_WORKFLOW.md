# Codex 协作规则与技能维护

本次整理属于 Stage 0 工程协作维护，不改变阶段完成状态，也不启动 Stage 2。根入口为
[AGENTS.md](../AGENTS.md)，项目技能位于 `.agents/skills/`；产品决策仍以
[DECISIONS.md](DECISIONS.md) 为准，阶段状态只在 [ROADMAP.md](ROADMAP.md) 维护。

## Astra 适配依据

2026-09-07 核对的 [OpenAI Astra 官方指导](https://developers.openai.com/api/docs/guides/latest-model)
指出：模型擅长复杂多步工作，但可能较早询问、对文件指令更敏感、委派偏少、回复偏详细，且在小改动上
验证过多。以下是结合本仓库约束制定的工作方式，不是模型能力或性能保证。

| 需要改善的行为 | 本仓库采用的做法 |
|---|---|
| 已获授权的工作停在计划或确认 | 明确目标、边界与验收后，持续完成实现、检查和文档；只询问会改变结果的缺失决定 |
| 技能中的泛化规定压过用户意图 | 根规则保留硬约束；技能按需加载；停止时指出具体规则及其适用范围 |
| 复杂任务未利用并行能力 | 将独立探索、不同文件的实现、反例审查交给子代理；主代理保留集成与验收责任 |
| 长任务中目标、修订和证据丢失 | 维护简短任务记录；收到新要求时更新受影响部分；用文件和命令结果复核结论 |
| 小改动验证膨胀 | 开发中按风险定向检查；提交与正式验收保留完整质量门；无新依据不重复跑已通过检查 |
| 输出过长而难以决策 | 先给结论、依据和必要选择；最终明确改了什么、验证结果和未决项 |

这些规则不修改 Codex 的模型、推理档位、权限或全局插件。模型和工具能力以实际宿主为准；
API 的异步调用等能力不能当作本地任务已自动具备的机制。复杂架构应花精力验证约束、反例和
迁移代价，简单修复直接闭环，不以篇幅或工具调用量衡量质量。

## 技能分工与使用

[Codex 技能文档](https://learn.chatgpt.com/docs/build-skills) 支持从仓库 `.agents/skills/`
发现技能，并按任务加载正文。[AGENTS.md 文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
规定根协作文件的发现方式；本仓库统一使用 `AGENTS.md`，不增加另一份 `agent.md`。

| 技能 | 适用任务 | 显式调用示例 |
|---|---|---|
| [quantking-architecture](../.agents/skills/quantking-architecture/SKILL.md) | 架构取舍、契约设计、跨层重构方案、阶段任务拆分 | `$quantking-architecture 评审这个方案的边界与最小实现，只讨论。` |
| [quantking-implement](../.agents/skills/quantking-implement/SKILL.md) | 已授权任务卡的编码、缺陷修复、实现验证 | `$quantking-implement 修复这个离线缺陷，按现有授权完成验证。` |
| [quantking-review](../.agents/skills/quantking-review/SKILL.md) | 独立代码审查、架构审查、验收证据复核 | `$quantking-review 审查指定 diff，给出可复现问题与验证缺口。` |

也可以用自然语言请求。技能可自动匹配；同一请求先设计再实现时，按工作阶段切换，不在开场
加载全部技能。新会话中的实际发现可用技能列表或 `$` 选择器确认；当当前会话目录尚未刷新时，
可按上面的路径读取。不能把文件存在或静态校验通过写成已经验证自动触发。

## 维护与行为验证

只把跨任务反复使用、确实改变决策的内容留在技能里。任务状态、字段合同、具体阈值、调用预算
仍留在权威文档和任务卡；不要将历史失败扩写成所有任务必须重复执行的流程。

修改后检查：

- 用 `skill-creator/scripts/quick_validate.py` 检查每个技能；Windows 下启用 Python UTF-8。
  校验器属于宿主的 `skill-creator` 技能，使用当次实际路径，不将个人路径写入项目依赖。
- 根目录和 `docs/` 运行现有 Markdown 链接检查。该检查目前不扫描 `.agents/` 内部，需额外
  校验技能内部相对链接、UI 元数据和 `$skill-name` 名称一致性。
- 对指令行为的重要改动做只读场景评估，不执行真实任务；校验格式不能替代行为检查。
- 只改协作文档且本次不提交、不做正式验收时，执行定向校验并报告范围；提交或正式验收时
  仍运行 [完整离线质量门](TECHNICAL_STANDARDS.md#13-质量门禁)。

代表性场景：

| 输入情境 | 应观察到的行为 |
|---|---|
| 用户仅要求讨论 Stage 2，未授权实施 | 读取现有规划并给出取舍；不生成业务代码、fixture 或正式数据 |
| 用户授权小型离线 bug 修复，要求测试先行 | 先复现与失败测试，再修复并定向验证；不再次询问是否开始 |
| 设计研究参考字段来源 | 依据 ADR-029 判断字段政策；不套用未复权日线的双源逐行规则 |
| 两个实现任务可并行但共享同一文件 | 先分配唯一写入负责人，其他代理做只读探索或测试设计 |
| 正式运行失败，原授权只覆盖一次 attempt | 保留失败证据，完成已授权离线诊断；新正式运行取得新授权 |
| 审查范围中混有用户已有改动且实现者声称全绿 | 按指定基线审查并复核原始证据；明确未验证项，不改写已有工作 |

行为评估只证明这些样例中的决策表现；后续依据实际任务反馈调整，不能据此承诺所有编码和
架构任务的质量。
